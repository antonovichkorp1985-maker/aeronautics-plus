# Технический прототип соосного вертолётного ротора

> **Архивный документ.** Он описывает ранний моноблочный prototype/API proof и не
> является текущим заданием на реализацию. Актуальная нормативная архитектура:
> [`MICRO_ASSEMBLED_ROTOR.md`](../../architecture/MICRO_ASSEMBLED_ROTOR.md). Здесь
> сохранены только проверенные сведения о Flywheel/API и происхождение решений.

Исторический статус: API и схема анимации были проверены по Create Aeronautics 1.3.2;
игровой узел намеренно не регистрировался.

> Архитектурное уточнение v2: финальная система не является одним готовым блоком.
> Игрок собирает микродетали внутри центральной ячейки по принципу Chisels & Bits,
> а лопасти выходят на несколько блоков. Контейнер, коллизии и сменные насадки описаны
> в актуальной архитектуре выше. Этот документ сохраняет результаты проверки Flywheel
> и физики, которые остаются применимыми к микросборке.

## Результат проверки API

### 1. Раздельное вращение технически возможно

`BasePropellerBlockEntity` уже хранит сглаженные `previousAngle`/`angle`, а
`SimplePropellerVisual` создаёт отдельный Flywheel `OrientedInstance` для вращаемой
модели винта. `GyroscopicPropellerBearingVisual` подтверждает, что один block entity
может безопасно владеть несколькими независимо трансформируемыми instance.

Следовательно, для соосного узла не нужны два полноразмерных Minecraft-блока или
один склеенный OBJ. Один внутренний контейнер микросборки создаёт два partial model
instance и каждый кадр задаёт им углы противоположного знака. Верхняя и нижняя
втулки, насадки, кольца, тяги и лопасти при этом остаются отдельными устанавливаемыми
деталями, а не заранее готовым блоком.

Компилируемый proof находится в:

```text
src/main/java/dev/leeeonidys/aeronauticsplus/client/CoaxialRotorVisualPrototype.java
src/main/java/dev/leeeonidys/aeronauticsplus/content/rotor/CoaxialRotorKinematics.java
```

Он использует:

```text
upperAngle = +2 * lerp(previousAngle, angle, partialTick)
lowerAngle = -2 * lerp(previousAngle, angle, partialTick)
```

`ROTOR_UPPER` и `ROTOR_LOWER` являются двумя разными `OrientedInstance`, поэтому
скорость, фаза и направление могут изменяться независимо. Сейчас proof использует
одну кинетическую скорость Create и инвертирует нижний угол.

### 2. Общий и циклический шаг

`GyroscopicPropellerBearingBlockEntity` предоставляет публичные `setTilt` и
`setStrictTilt`, строит `tiltQuat` и передаёт наклон в направление тяги. Текущая
реализация Create Aeronautics ограничивает наклон конусом 12°. Это подходит как
первая основа циклического шага, но для полноценного управления требуется отдельный
контроллер ввода, а не прямой вызов метода модели.

Blender-объекты `SWASHPLATE_FIXED`, `SWASHPLATE_ROTATING`, `PITCH_LINKS_LOWER` и
`PITCH_LINKS_UPPER` поэтому отделены от роторов. Кольца получают общий quaternion
наклона, а вращающееся кольцо и тяги дополнительно следуют нужной втулке.

### 3. Физика и ограничения

`BasePropellerBlockEntity` создаёт один `PropellerActorBehaviour` и один вектор тяги.
Сам behaviour поддерживает несколько слоёв диска через `addPropellerLayer`, но сила
остаётся общей для всего узла.

Для первого соосного ротора это корректная безопасная схема:

- две независимо вращаемые визуальные модели;
- один суммарный источник тяги, настроенный под пару роторов;
- отсутствие двойного начисления силы из-за двух визуальных дисков.

Но визуальная встречная раскрутка сама по себе не создаёт реактивный момент. Если в
будущем потребуется физическое управление рысканием разницей коллективного шага,
нужно будет реализовать два отдельных канала силы/момента в Sable, а не просто
изменить скорость одной из моделей.

## Почему proof пока не зарегистрирован как блок

Это намеренное ограничение небольшого безопасного шага:

1. нет принятой финальной Blender-модели;
2. требуется проверить fallback renderer и Flywheel visual в реальном клиенте;
3. до игрового теста нельзя фиксировать баланс тяги и рецепт;
4. незавершённый блок не должен попадать в творческую вкладку или survival-мир.

После получения экспортированных `coaxial_rotor_upper.obj`,
`coaxial_rotor_lower.obj` и `coaxial_rotor_static.obj` следующий шаг — зарегистрировать
экспериментальный блок, fallback BER и Flywheel visual и проверить:

- два встречных направления при положительных и отрицательных RPM;
- паузу/интерполяцию на нулевой скорости;
- все шесть направлений установки;
- видимость на обычном уровне и внутри Sable sublevel;
- Sodium/Flywheel и vanilla fallback path;
- суммарную тягу без удвоения.
