# Blender-шаблон вертолётного и соосного ротора

Статус: техническая спецификация v1.0 для Aeronautics Plus v0.3.

Генератор сцены:

```text
scripts/blender/create_helicopter_rotor_template.py
```

Создание готового `.blend` в Blender 4.x:

```bash
blender --background \
  --python scripts/blender/create_helicopter_rotor_template.py -- \
  --output AeronauticsPlus-Helicopter-Rotor-Template.blend
```

В рабочем окружении проекта Blender не установлен, поэтому в Git хранится
воспроизводимый генератор шаблона, а не непрозрачный бинарный `.blend`.

## 1. Масштаб и координаты

- `1 Blender metre = 1 Minecraft block`.
- В Blender вверх направлена ось `+Z`.
- При экспорте OBJ: `Forward = -Z`, `Up = Y`.
- После экспорта Blender `+Z` становится Minecraft `+Y`.
- Ось мачты и вращения в Blender: `+Z`; в Minecraft: `+Y`.
- Центр блока в Minecraft: `(0.5, 0.5, 0.5)`.
- Соответствующая точка в Blender при указанном преобразовании экспорта:
  `(0.5, -0.5, 0.5)`.
- Нельзя применять произвольный дополнительный масштаб при экспорте; Scale = `1.0`.

## 2. Обязательные объекты

Имена считаются частью контракта с кодом и должны сохраняться:

| Объект | Назначение | Положение origin в Blender | Движение |
|---|---|---|---|
| `STATIC_MOUNT` | корпус и основание узла | центр собственной геометрии | нет |
| `STATIC_MAST` | короткая мачта | на оси `(0.5, -0.5)` | нет |
| `SWASHPLATE` | автомат перекоса | `(0.5, -0.5, 0.40)` | отдельный tilt |
| `ROTOR_LOWER` | нижний ротор соосной пары | `(0.5, -0.5, 0.56)` | вращение вокруг локальной `+Z` |
| `ROTOR_UPPER` | верхний ротор соосной пары | `(0.5, -0.5, 0.78)` | независимое вращение вокруг локальной `+Z` |
| `AP_ROOT__MC_BLOCK_CENTER` | направляющая центра блока | `(0.5, -0.5, 0.5)` | не экспортировать |
| `AXIS_*__NO_EXPORT` | направляющие осей | на pivot соответствующего ротора | не экспортировать |

`ROTOR_UPPER` и `ROTOR_LOWER` нельзя объединять в один объект или запекать в
`STATIC_MOUNT`: runtime создаёт для них два разных Flywheel instance.

OBJ не хранит Blender-origin как игровой pivot. Origin нужен для авторинга и
проверки; игровой renderer вращает обе модели вокруг общей оси мачты, проходящей
через Minecraft `(X=0.5, Z=0.5)`. Высота ротора задаётся вершинами модели.

## 3. Направления вращения

Если смотреть сверху вдоль Blender `-Z` на origin:

- `ROTOR_UPPER`: против часовой стрелки (`CCW`, положительный угол);
- `ROTOR_LOWER`: по часовой стрелке (`CW`, отрицательный угол).

В коде используется один интерполированный базовый угол:

```text
upperAngle = +baseAngle
lowerAngle = -baseAngle
```

Фазы шаблона: верхний ротор `0°`, нижний `45°`. Это предотвращает визуальное
совпадение лопастей в неподвижном состоянии и облегчает проверку двух instance.

## 4. Размеры направляющей геометрии

Шаблон создаёт не финальную художественную модель, а корректный масштабный макет:

- число лопастей каждого ротора: `4`;
- радиус: `2.50` блока;
- диаметр: `5.00` блоков;
- радиус втулки: `0.22` блока;
- начало лопасти: `0.29` блока;
- корневая хорда: `0.34` блока;
- концевая хорда: `0.14` блока;
- толщина: `0.055` блока;
- базовый угол установки: `+8°` сверху и `-8°` снизу;
- стреловидность направляющей: `4°`;
- видимая мачта остаётся короткой и не выступает далеко за механизм.

Лопасть должна иметь непрерывное сужение, плавный профиль и различимую переднюю
кромку. Не превращать её в длинный прямоугольный cuboid.

## 5. Материалы и UV

Обязательные material slots:

- `AP_METAL` — втулки, мачта и крепёж;
- `AP_MECHANISM` — автомат перекоса и тяги;
- `AP_BLADE` — основная поверхность лопастей;
- `AP_BLADE_TIP` — контрастные законцовки.

Требования:

1. UV находятся в диапазоне `0..1`.
2. Повторяющиеся лопасти могут использовать один и тот же UV-остров.
3. Законцовки должны иметь отдельный остров/материал.
4. Не оставлять нулевые UV-полигоны и растянутые боковые грани.
5. Нормали направлены наружу; перед экспортом выполнить Recalculate Outside.
6. Scale каждого экспортируемого объекта: `(1, 1, 1)`.
7. Mesh должен быть триангулирован; не экспортировать n-gon и направляющие.

Рекомендуемый атлас — 32×32 для прототипа либо 64×64 для финальной втулки с
мелкими механическими деталями. Чужие модели и текстуры не использовать.

## 6. Раздельный экспорт

Экспортировать как минимум три файла:

```text
coaxial_rotor_static.obj
coaxial_rotor_lower.obj
coaxial_rotor_upper.obj
```

Опционально `SWASHPLATE` экспортируется четвёртым файлом, если tilt будет
анимироваться отдельно:

```text
coaxial_rotor_swashplate.obj
```

Для каждого файла включать только нужные mesh-объекты, `Selection Only`, UV,
материалы и нормали. Анимацию и armature в OBJ не экспортировать — углы задаёт код.

## 7. Проверка перед передачей

- два rotor-объекта действительно отделены;
- оба origin лежат на одной оси мачты;
- верхний и нижний ротор не пересекаются при фазах `0°/45°`;
- лопасти не кубические и не имеют чрезмерной толщины;
- короткая мачта не торчит за пределы механизма без необходимости;
- нет отрицательного unapplied scale;
- после тестового OBJ-экспорта размеры остаются ровно 5 блоков по диску;
- имена объектов и материалов совпадают со спецификацией.
